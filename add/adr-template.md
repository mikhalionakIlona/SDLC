
ADR-001 — Выбор архитектуры и технологического стека NutriFlow
Статус: Accepted
Дата: 02.11.2026
Лицо, принимающее решение: архитектор/разработчик
Консультируемые: заказчик (учебная модель), разработчик
Информируемые: команда проекта, преподаватель

Название
Локально-ориентированное Android-приложение с многослойной архитектурой и Room/SQLite.

---

## 1. Контекст и проблема
NutriFlow — Android-дневник питания и водного баланса. Требуются ручной ввод еды, учет воды, цели, штрихкод, напоминания и статистика. Согласно границам проекта из лабораторной работы №3, серверная учетная запись и синхронизация не предусмотрены. Основные функции должны работать офлайн; интернет нужен для получения данных о неизвестном продукте.

---

## 2. Факторы решения
Соответствие Android 8.0+ и навыкам проекта.
Офлайн-доступность и локальное хранение.
Доступ к камере, уведомлениям и фоновым задачам.
Простота разработки и тестирования.
Отсутствие необходимости в backend.

---

## 3. Рассмотренные альтернативы
A. Нативный Android: Java + Room/SQLite + CameraX/ZXing + WorkManager
Плюсы: прямой доступ к API Android, зрелые библиотеки, локальная работа, одна платформа в рамках текущего объема. Минусы: только Android; требуется корректная работа с разрешениями и жизненным циклом.

B. Кроссплатформенное приложение (например, Flutter)
Плюсы: возможность повторного использования UI-кода для нескольких платформ. Минусы: дополнительное освоение стека; iOS/web не входят в текущие требования; плагины камеры и фоновых задач добавляют интеграционные риски.

C. Веб-приложение с серверной БД
Плюсы: доступ из браузера и централизованное хранение. Минусы: необходим backend и сеть; решение противоречит локально-ориентированным границам и увеличивает объем разработки.

---

## 4. Решение
Выбрать вариант A: Java 17, Android SDK, XML/Material Components, Room поверх SQLite, CameraX/ZXing, WorkManager, MPAndroidChart и Open Food Facts. Архитектура разделяется на Presentation, Domain, Data и Integration. UI работает через репозитории; локальные данные не отправляются на сервер NutriFlow.

---

## 5. Последствия
Положительные: основные сценарии работают офлайн; нет серверной инфраструктуры; разделение слоев упрощает тестирование и развитие.
Отрицательные/риски: нет синхронизации; приложение только для Android; внешний каталог может не содержать нужный продукт; напоминания зависят от разрешений и ограничений Android.
Снижение рисков: ручное создание продукта, обработка отсутствия сети, проверка разрешений, тестирование расчетов и репозиториев.

---

## 6. Подтверждение
Решение принято как основа SDD версии 1.0. Добавление CSV Export не меняет архитектуру: файл формируется из локального репозитория и сохраняется на устройстве.

---
