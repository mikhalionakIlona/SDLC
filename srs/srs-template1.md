## 1. Введение {#1-introduction}

➥ Документ описывает бизнес-требования к мобильному приложению NutriFlow для ежедневного учёта питания и питьевого режима.

### 1.1 Назначение документа {#11-document-purpose}

➥ Спецификация фиксирует, что должно делать приложение NutriFlow, а не то, как оно будет реализовано. Документ предназначен для заказчика, разработчика, тестировщика и преподавателя. Документ ведётся в репозитории проекта, изменения вносятся через pull-request и фиксируются в истории изменений.

### 1.2 Область применения продукта {#12-product-scope}

➥ NutriFlow, версия 1.0, — Android-приложение, помогающее человеку контролировать суточное потребление калорий и воды. Пользователь записывает съеденное вручную или сканированием штрих-кода продукта, фиксирует выпитую воду, получает напоминания о воде и видит свой прогресс на экране и на графиках.

➥ Бизнес-цели:
сократить время на ввод данных о питании до нескольких секунд за счёт сканирования штрих-кодов;
помочь пользователю регулярно пить воду с помощью напоминаний;
дать наглядную обратную связь (прогресс за день, неделю и месяц), чтобы пользователь продолжал вести учёт.
Входит в версию 1.0: учёт приёмов пищи, сканирование штрих-кодов с получением данных из открытой базы продуктов, учёт воды, напоминания, визуализация прогресса, локальное хранение данных.
Не входит в версию 1.0: серверная часть и учётные записи, синхронизация между устройствами, iOS и web-версии, распознавание еды по фотографии, рекомендации по питанию, медицинские советы, социальные функции.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

➥ NutriFlow — новый автономный продукт, не заменяющий существующих систем. Приложение работает на смартфоне пользователя, все пользовательские данные хранит локально. Единственная внешняя зависимость — открытая база Open Food Facts, к которой приложение обращается при сканировании штрих-кода. Для напоминаний используется система уведомлений Android. Владелец продукта — Михалёнок И.А, SLA и платной поддержки нет. Контекстная диаграмма: Контекстная диаграмма

### 2.2 Функции продукта {#22-product-functions}

➥ Учёт приёмов пищи: добавление, просмотр, редактирование и удаление записей.
➥ Сканирование штрих-кода продукта камерой и автоматическая подстановка калорийности и БЖУ.
➥ Создание собственных продуктов, если продукта нет в базе; быстрый повторный ввод недавних и избранных продуктов.
➥ Установка дневной цели по калориям.
➥ Учёт воды: быстрое добавление порций, дневная цель по воде.
➥ Напоминания о воде по расписанию, заданному пользователем.
➥ Визуализация прогресса: итоги дня, графики за неделю и месяц.
➥ Работа без интернета для всего, кроме получения данных нового продукта по штрих-коду.

### 2.3 Ограничения продукта {#23-product-constraints}

- Приложение должно работать на Android 8.0 (API 26) и выше. Тип: внешнее. Обязательное.
- Приложение должно разрабатываться на языке Java с использованием Android SDK (интерфейс на XML-разметке). Тип: внутреннее. Предпочтительное.
- Данные о продуктах по штрих-коду должны браться из Open Food Facts. Тип: внешнее. Обязательное.
- Пользовательские данные должны храниться только на устройстве (локальная БД). Тип: внутреннее. Обязательное.
- Приложение не должно требовать регистрации и аккаунта. Тип: внутреннее. Обязательное.
- Приложение не должно использовать платные сервисы. Тип: внешнее. Обязательное.
- Приложение не должно давать медицинские рекомендации. Тип: внешнее. Обязательное.
- Интерфейс должен быть на русском языке. Тип: внутреннее. Обязательное.

### 2.4 Характеристики пользователей {#24-user-characteristics}

Занятый пользователь. Хочет следить за питанием, но не готов тратить время на ввод. Использует приложение ежедневно, 3–6 раз в день по несколько секунд. Потребности: максимально быстрый ввод, сканирование, напоминания.

Новичок в учёте питания. Не знает калорийность продуктов и своих норм. Использует приложение ежедневно, в первые недели. Потребности: простой интерфейс, подсказки при первом запуске, готовая цель по воде.

Пользователь с постоянным рационом. Ест примерно одно и то же. Использует приложение ежедневно. Потребности: избранные и недавние продукты.

Технической подготовки пользователей не требуется. Интерфейс на русском языке, размер шрифта должен учитывать системные настройки Android (доступность).

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

1. У пользователя есть смартфон на Android 8.0+ с камерой. Если это не так, сканирование недоступно. Смягчение: ручной ввод продукта работает без камеры (REQ-FUNC-001).
2. Open Food Facts доступна и сохраняет формат API. Если это не так, сканирование перестаёт находить продукты. Смягчение: ручное создание продукта (REQ-FUNC-003) и кэш найденных продуктов.
3. Данные Open Food Facts содержат калорийность не для всех продуктов. Часть продуктов найдётся неполными. Смягчение: пользователь может дополнить и исправить данные перед сохранением.
4. Пользователь разрешает показ уведомлений. Если нет, напоминания не приходят. Смягчение: приложение предупреждает об отключённых уведомлениях (REQ-FUNC-008).
5. Система Android не прерывает работу будильников в фоне. Если прерывает, напоминания приходят с задержкой. Смягчение: использование штатных средств планирования Android.

### 2.6 Распределение требований {#26-apportioning-of-requirements}

Итерация 1 (MVP). Ручной учёт питания и воды, цели. Требования: REQ-FUNC-001, 004, 005, 006, 007.

Итерация 2. Штрих-коды, свои продукты, быстрый ввод. Требования: REQ-FUNC-002, 003, 010.

Итерация 3. Напоминания и визуализация. Требования: REQ-FUNC-008, 009.

Отложено. Экспорт данных. Требование: REQ-FUNC-011.

Требования разделов 3.3–3.5 относятся ко всем итерациям, если не указано иное.

## 3. Требования {#3-requirements}

➥ Каждое функциональное требование описано по шаблону: ID, Title, Statement, Rationale, Acceptance Criteria, Verification Method. Нефункциональные требования приведены в ниже с теми же полями.

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

➥ Общие требования к интерфейсу:

REQ-INT-001

Statement: Интерфейс должен быть полностью на русском языке.
Acceptance Criteria: Все тексты экранов, уведомлений и сообщений об ошибках на русском.
Verification Method: Inspection

REQ-INT-002

Statement: Нижняя навигация должна давать доступ к экранам «Дневник», «Вода», «Прогресс», «Настройки» в одно нажатие.
Acceptance Criteria: Переход на любой из 4 экранов за 1 нажатие.
Verification Method: Demonstration

REQ-INT-003

Statement: Экраны со списками и графиками должны показывать понятное сообщение и подсказку действия в пустом состоянии и при ошибке.
Acceptance Criteria: Для пустого дня, отсутствия сети и отказа в доступе к камере отображается сообщение с предложением действия.
Verification Method: Test

REQ-INT-004

Statement: Интерфейс следует строить по рекомендациям Material Design и учитывать системный размер шрифта.
Acceptance Criteria: Текст масштабируется при увеличении шрифта системы до 130% без обрезания.
Verification Method: Test

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

➥ REQ-INT-005

Statement: Приложение должно использовать основную камеру смартфона для сканирования штрих-кодов форматов EAN-13, EAN-8, UPC-A.
Acceptance Criteria: Распознаётся штрих-код каждого из трёх форматов.
Verification Method: Test

REQ-INT-006

Statement: Приложение должно запрашивать разрешение на камеру только при первом открытии сканера и работать без него в остальных функциях.
Acceptance Criteria: При отказе в разрешении все функции, кроме сканера, доступны.
Verification Method: Test

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

➥ REQ-INT-007

Statement: Приложение должно получать данные продукта по штрих-коду запросом к API Open Food Facts (HTTPS, формат JSON): название, калории, белки, жиры, углеводы на 100 г.
Acceptance Criteria: Для известного штрих-кода получены название и калорийность на 100 г.
Verification Method: Test

REQ-INT-008

Statement: При таймауте (10 с), ошибке сети или кодах ответа 4xx/5xx приложение должно сообщить об ошибке и предложить ручной ввод, не завершаясь аварийно.
Acceptance Criteria: В режиме «без сети» и при недоступном сервисе показано сообщение, приложение продолжает работу.
Verification Method: Test

REQ-INT-009

Statement: Приложение должно использовать систему уведомлений Android для напоминаний и запрашивать разрешение на уведомления (Android 13+).
Acceptance Criteria: Уведомление приходит по расписанию при выданном разрешении.
Verification Method: Test

Аутентификация в Open Food Facts не требуется. Политика версий: используется актуальная версия API, при несовместимых изменениях требуется изменение по REQ-CM-001.

### 3.2 Функциональные требования {#32-functional}

REQ-FUNC-001

Title: Ручное добавление записи о приёме пищи
Statement: Система должна позволять пользователю добавить запись: название, масса порции (г), калории, белки, жиры, углеводы, тип приёма пищи, дата и время.
Rationale: Базовая функция учёта; работает без камеры и интернета.
Acceptance Criteria: Запись сохраняется и отображается в дневнике выбранной даты; поля «название» и «калории» обязательны; масса от 1 до 5000 г; калории от 0 до 5000 ккал на запись; при неверных значениях показывается ошибка и запись не сохраняется.
Verification Method: Test
More Information: Макет mockup-product.png.

REQ-FUNC-002

Title: Добавление продукта сканированием штрих-кода
Statement: Система должна по сканированию штрих-кода находить продукт в Open Food Facts, подставлять название и пищевую ценность на 100 г и пересчитывать калории и БЖУ на введённую пользователем массу порции.
Rationale: Сокращает время ввода и ошибки при ручном вводе.
Acceptance Criteria: От наведения камеры до экрана с найденным продуктом проходит не более 5 с при хорошей связи и освещении; при порции 150 г и калорийности 200 ккал/100 г отображается 300 ккал; пользователь может изменить любое поле перед сохранением.
Verification Method: Test
More Information: REQ-INT-005, REQ-INT-007, mockup-scanner.png.

REQ-FUNC-003

Title: Продукт не найден или данные неполные
Statement: Если продукт не найден или у него нет данных о калориях, система должна сообщить об этом и предложить заполнить карточку вручную; введённый продукт должен сохраняться локально и находиться при повторном сканировании того же штрих-кода без обращения к сети.
Rationale: Open Food Facts не покрывает все продукты.
Acceptance Criteria: Для несуществующего штрих-кода показано сообщение и форма ручного ввода с уже заполненным штрих-кодом; при повторном сканировании продукт находится в режиме «без сети».
Verification Method: Test

REQ-FUNC-004

Title: Дневник питания за выбранную дату
Statement: Система должна показывать записи за выбранную дату, сгруппированные по приёмам пищи, с суммарными калориями и БЖУ за каждую группу и за день, и позволять редактировать и удалять записи.
Rationale: Основной экран приложения.
Acceptance Criteria: Итоги за день равны сумме записей; после редактирования и удаления итоги обновляются сразу; можно выбрать любую дату в прошлом; удаление требует подтверждения или возможности отмены.
Verification Method: Test

REQ-FUNC-005

Title: Дневная цель по калориям
Statement: Система должна позволять пользователю задать дневную цель по калориям и показывать остаток или превышение на экране дневника.
Rationale: Без цели прогресс невозможно оценить.
Acceptance Criteria: Допустимые значения цели 800–6000 ккал, иначе ошибка ввода; цель по умолчанию 2000 ккал; при превышении цели индикатор меняет цвет и отображается превышение в ккал; изменение цели не меняет данные прошлых дней.
Verification Method: Test
More Information: Нижняя граница снижает риск неверного использования приложения, см. REQ-COMP-002.

REQ-FUNC-006

Title: Учёт выпитой воды
Statement: Система должна позволять добавлять порции воды кнопками быстрого ввода (150, 250, 500 мл), вводом произвольного объёма и отменять последнее добавление.
Rationale: Вода записывается много раз за день, ввод должен занимать одно нажатие.
Acceptance Criteria: Нажатие кнопки быстрого ввода добавляет запись и обновляет итог за день менее чем за 1 с; произвольный объём 10–2000 мл; отмена последней записи уменьшает итог; список записей воды за день можно просмотреть и удалить запись.
Verification Method: Test
More Information: mockup-water.png.

REQ-FUNC-007

Title: Дневная цель по воде
Statement: Система должна позволять задать дневную цель по воде и показывать прогресс в процентах и миллилитрах.
Rationale: Цель мотивирует и определяет логику напоминаний.
Acceptance Criteria: Цель по умолчанию 2000 мл, допустимый диапазон 500–6000 мл; при достижении цели показывается сообщение о выполнении; прогресс может превышать 100%.
Verification Method: Test

REQ-FUNC-008

Title: Напоминания о воде
Statement: Система должна присылать уведомления о необходимости выпить воду с интервалом (30 мин – 4 ч) в заданном пользователем окне времени (по умолчанию 09:00–21:00), позволять включать и отключать напоминания, и не присылать уведомления после достижения дневной цели.
Rationale: Напоминания — одна из ключевых бизнес-целей.
Acceptance Criteria: Уведомление приходит в пределах ±2 минут от расчётного времени при выданном разрешении; вне окна времени уведомлений нет; после достижения цели уведомления до следующего дня не приходят; из уведомления можно добавить порцию воды без открытия приложения; если уведомления отключены в системе, в настройках показывается предупреждение; расписание сохраняется после перезагрузки телефона.
Verification Method: Test
More Information: REQ-INT-009, mockup-settings.png.

REQ-FUNC-009

Title: Визуализация прогресса
Statement: Система должна показывать прогресс за день (кольцо или полоса для калорий и воды) и графики калорий и воды за последние 7 и 30 дней с отметкой цели.
Rationale: Наглядная обратная связь повышает вовлечённость.
Acceptance Criteria: Данные на графиках совпадают с суммами по дням в дневнике; дни без записей отображаются явно как отсутствие данных, а не как ноль; переключение 7/30 дней занимает менее 1 с; средние значения за период отображаются под графиком.
Verification Method: Test
More Information: mockup-progress.png.

REQ-FUNC-010

Title: Недавние и избранные продукты
Statement: Система должна показывать при добавлении записи список недавних продуктов (последние 20) и позволять отметить продукт избранным.
Rationale: Пользователи часто едят одно и то же; ускоряет ввод.
Acceptance Criteria: Продукт из списка добавляется в дневник не более чем за 3 нажатия; избранные отображаются выше недавних; продукт можно убрать из избранного.
Verification Method: Demonstration

REQ-FUNC-011

Title: Экспорт данных
Statement: Система может позволять экспортировать записи за выбранный период в CSV-файл.
Rationale: Позволяет пользователю сохранить данные и передать специалисту.
Acceptance Criteria: Файл открывается в табличном редакторе, содержит дату, название, массу, калории, БЖУ и объём воды.
Verification Method: Test
More Information: Отложено на следующие итерации.
