## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ представляет собой Спецификацию требований к программному обеспечению (SRS) для мобильного приложения «NutriFlow». Его главная задача – чётко определить границы проекта и зафиксировать ЧТО именно должна делать система, оставляя при этом пространство для инженерных решений относительно того, КАК это будет реализовано.

Документ выступает главным ориентиром для всех участников проекта, определяя зоны их ответственности:

Команда разработки – использует спецификацию как основу для декомпозиции задач и реализации функциональности;
Инженеры по тестированию – опираются на требования при составлении тест-планов и критериев приёмки;
Заказчик – сверяет по документу, насколько итоговый продукт закрывает его бизнес-потребности;
Преподаватель – проводит оценку качества проектирования и проверку артефактов на протяжении жизненного цикла продукта.

Связанные документы: бизнес-требования от Заказчика, а также модели экранов на языке SysMLv2 и макеты пользовательских интерфейсов, созданные на этапе проектирования.

### 1.2 Область применения продукта {#12-product-scope}

«NutriFlow» 0.1 – мобильное приложение для Android, помогающее человеку вести ежедневный учёт съеденного и выпитой воды. Пользователь записывает приёмы пищи вручную или сканированием штрих-кода продукта, фиксирует воду, получает напоминания о воде и наглядно видит свой прогресс за день, неделю и месяц.

Бизнес-цели:

сократить время ввода данных о питании до нескольких секунд за счёт сканирования штрих-кодов;
помочь пользователю регулярно пить воду с помощью напоминаний;
дать наглядную обратную связь о прогрессе, чтобы пользователь продолжал вести учёт.

Входит в область применения:

учёт приёмов пищи (добавление вручную, просмотр, редактирование и удаление записей по датам);
сканирование штрих-кода продукта и получение его пищевой ценности из открытой базы Open Food Facts;
создание собственных продуктов, недавние и избранные продукты;
дневные цели по калориям и воде;
учёт выпитой воды и напоминания о воде по расписанию;
визуализация прогресса: итоги дня и графики за 7 и 30 дней;
локальное хранение всех данных на устройстве.

Не входит в область применения (в текущей версии):

серверная часть, учётные записи и синхронизация данных между устройствами (все данные остаются на смартфоне);
версии для iOS и web (система реализуется исключительно как Android-приложение);
распознавание еды по фотографии;
рекомендации по питанию, расчёт персональных норм и любые медицинские советы (приложение только ведёт учёт);
социальные функции и обмен данными с другими пользователями.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

«NutriFlow» – новый самостоятельный продукт. Ранее человеку, который хотел следить за питанием и водой, приходилось вести записи в заметках и таблицах, искать калорийность продуктов вручную в интернете и пользоваться отдельным приложением-напоминалкой о воде. Это долго, и поэтому учёт быстро бросают. Приложение объединяет учёт еды, учёт воды, напоминания и прогресс в одном месте и ускоряет ввод за счёт сканирования штрих-кодов.

Приложение работает на смартфоне пользователя и хранит все данные локально, без серверной части.

Внешние системы и зависимости:

Open Food Facts – открытая база продуктов, из которой по штрих-коду берутся название и пищевая ценность на 100 г.
Система уведомлений Android – для показа напоминаний о воде в заданное время.
Камера устройства – для сканирования штрих-кодов.

### 2.2 Функции продукта {#22-product-functions}

Основные функциональные возможности мобильного приложения «NutriFlow»:

Добавление приёмов пищи вручную и просмотр дневника питания по датам.
Сканирование штрих-кода продукта и автоматическая подстановка калорийности и БЖУ.
Создание собственных продуктов, недавние и избранные продукты для быстрого ввода.
Установка дневных целей по калориям и воде.
Учёт выпитой воды с кнопками быстрого ввода.
Напоминания о воде по расписанию, заданному пользователем.
Визуализация прогресса: итоги дня, графики калорий и воды за 7 и 30 дней.
Работа без интернета для всех функций, кроме получения данных нового продукта по штрих-коду.

### 2.3 Ограничения продукта {#23-product-constraints}

При разработке мобильного приложения «NutriFlow» должны соблюдаться следующие ограничения:

Только Android: система реализуется исключительно как приложение для Android 8.0 (API 26) и выше, без версий для iOS и web.
Язык интерфейса: пользовательский интерфейс должен быть полностью на русском языке.
Без серверной части и аккаунтов: все данные хранятся только на устройстве, регистрация не требуется.
Внешние интеграции: для получения данных о продуктах система должна использовать открытый API Open Food Facts; платные сервисы не используются.
Без медицинских рекомендаций: приложение ведёт учёт, но не даёт советов по питанию и не рассчитывает персональные нормы.
Законодательство: система должна соответствовать Закону РБ «О защите персональных данных» (обеспечивать безопасное хранение и обработку данных пользователя).
Технологический стек: приложение должно быть реализовано на языке Java с использованием Android SDK (интерфейс на XML-разметке), локальная база данных – Room (SQLite).

### 2.4 Характеристики пользователей {#24-user-characteristics}

У системы «NutriFlow» нет разделения прав доступа: приложение однопользовательское, и все данные принадлежат владельцу устройства. Различаются типичные сценарии использования:

Занятый пользователь – хочет следить за питанием, но не готов тратить время на ввод. Использует приложение ежедневно по 3–6 раз в день по несколько секунд. Нужны быстрый ввод, сканирование штрих-кодов и напоминания. Уровень подготовки: базовый.
Новичок в учёте питания – не знает калорийность продуктов и своих норм. Использует приложение ежедневно в первые недели. Нужны простой интерфейс, понятные подсказки и готовая цель по воде по умолчанию. Уровень подготовки: базовый.
Пользователь с постоянным рационом – ест примерно одно и то же. Использует приложение ежедневно. Нужны избранные и недавние продукты. Уровень подготовки: средний.

Особенности поведения и UX:

Приложение используется преимущественно одной рукой и на ходу, поэтому основные действия (добавить воду, запустить сканер) должны выполняться за 1–2 нажатия.
Интерфейс должен быть интуитивно понятным, так как целевая аудитория включает людей разного возраста и разного уровня подготовки.
Техническая подготовка пользователей не требуется.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

1. У пользователя есть смартфон на Android 8.0+ с камерой. Если это не так, сканирование недоступно. Смягчение: ручной ввод продукта работает без камеры (REQ-FUNC-001).
2. Open Food Facts доступна и сохраняет формат API. Если это не так, сканирование перестаёт находить продукты. Смягчение: ручное создание продукта (REQ-FUNC-003) и кэш найденных продуктов.
3. Данные Open Food Facts содержат калорийность не для всех продуктов. Часть продуктов найдётся неполными. Смягчение: пользователь может дополнить и исправить данные перед сохранением.
4. Пользователь разрешает показ уведомлений. Если нет, напоминания не приходят. Смягчение: приложение предупреждает об отключённых уведомлениях (REQ-FUNC-008).
5. Система Android не прерывает работу будильников в фоне. Если прерывает, напоминания приходят с задержкой. Смягчение: использование штатных средств планирования Android.

### 2.6 Распределение требований {#26-apportioning-of-requirements}

Основные требования к системе «NutriFlow» распределены по функциональным компонентам (модулям). Перекрёстные ссылки показывают, какой модуль отвечает за реализацию тех или иных требований:

Дневник питания – REQ-FUNC-001, REQ-FUNC-004, REQ-FUNC-005, REQ-INT-001, REQ-INT-003. Ручное добавление записей, просмотр по датам, редактирование, удаление, недавние и избранные продукты.
Сканер и данные о продуктах – REQ-FUNC-002, REQ-FUNC-003, REQ-INT-002, REQ-INT-010, REQ-INT-011, REQ-INT-013, REQ-INT-014, REQ-AI-001…REQ-AI-008. Работа с камерой, распознавание штрих-кода, получение и проверка данных Open Food Facts, ручное создание продукта.
Цели и вода – REQ-FUNC-006, REQ-FUNC-007, REQ-FUNC-008, REQ-INT-004. Цели по калориям и воде, учёт выпитой воды.
Напоминания – REQ-FUNC-009, REQ-INT-015. Расписание и показ уведомлений о воде.
Прогресс – REQ-FUNC-010, REQ-FUNC-011, REQ-INT-005. Итоги дня и графики за 7 и 30 дней.
Настройки и первый запуск – REQ-FUNC-012, REQ-FUNC-013, REQ-INT-006, REQ-COMP-002. Настройка целей и напоминаний, первичное уведомление, экспорт данных.
Хранилище данных – REQ-INT-016, REQ-REL-001, REQ-SEC-001, REQ-SEC-005. Локальная база данных Room.

Распределение по итерациям разработки:

Итерация 1 (MVP): ручной учёт питания и воды, дневные цели – REQ-FUNC-001, 004, 006, 007, 008.
Итерация 2: сканирование штрих-кодов, собственные продукты, быстрый ввод – REQ-FUNC-002, 003, 005 и REQ-AI-001…008.
Итерация 3: напоминания и визуализация прогресса – REQ-FUNC-009, 010, 011.
Отложено: экспорт данных (REQ-FUNC-013).

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

REQ-INT-001: Экран «Дневник»

Title: Главный экран дневника питания.
Statement: Система должна предоставлять главный экран «Дневник» с выбором даты, индикатором остатка калорий, суммами БЖУ, секциями «Завтрак», «Обед», «Ужин», «Перекус» со списками записей и кнопкой добавления.
Rationale: Пользователь должен сразу видеть, сколько он съел и сколько осталось до цели.
Acceptance Criteria: После запуска приложения открывается экран «Дневник» за текущую дату, все перечисленные блоки отображаются на одном экране и корректно умещаются в окно устройства.
Verification Method: Demonstration.

REQ-INT-002: Экран «Сканер штрих-кода»

Title: Экран сканирования.
Statement: Система должна предоставлять экран сканера с изображением камеры, рамкой наведения, подсказкой «Наведите камеру на штрих-код», кнопкой «Ввести вручную» и кнопкой включения вспышки.
Rationale: Сканирование – главный способ ускорить ввод данных о питании.
Acceptance Criteria: Экран открывается из дневника нажатием кнопки добавления; кнопка «Ввести вручную» ведёт к форме без сканирования.
Verification Method: Demonstration.

REQ-INT-003: Экран «Карточка продукта»

Title: Подтверждение и редактирование продукта.
Statement: Система должна предоставлять карточку продукта с названием, пищевой ценностью на 100 г, полем массы порции, расчётом на порцию, выбором приёма пищи и кнопкой «Сохранить».
Rationale: Пользователь подтверждает или исправляет данные до добавления в дневник (см. REQ-AI-007).
Acceptance Criteria: Все поля карточки редактируются; при изменении массы порции расчёт обновляется сразу; при пустом названии или нулевой массе кнопка «Сохранить» неактивна или выводится сообщение об ошибке.
Verification Method: Test.

REQ-INT-004: Экран «Вода»

Title: Учёт воды.
Statement: Система должна предоставлять экран «Вода» с индикатором прогресса (выпито из цели, процент), кнопками быстрого ввода порций, кнопками «Другой объём» и «Отменить» и списком записей воды за день.
Rationale: Вода записывается много раз за день, поэтому управление должно быть максимально простым.
Acceptance Criteria: Все перечисленные элементы отображаются на одном экране; нажатие на кнопку порции обновляет индикатор.
Verification Method: Demonstration.

REQ-INT-005: Экран «Прогресс»

Title: Графики и итоги.
Statement: Система должна предоставлять экран «Прогресс» с переключателем периода (7 или 30 дней), графиками калорий и воды с отметкой цели и блоком средних значений за период.
Rationale: Наглядная динамика мотивирует продолжать учёт.
Acceptance Criteria: Переключатель меняет период обоих графиков; линия цели отображается на каждом графике; средние значения указаны под графиками.
Verification Method: Demonstration.

REQ-INT-006: Экран «Настройки»

Title: Цели, напоминания, сведения о приложении.
Statement: Система должна предоставлять экран «Настройки» для изменения целей по калориям и воде, управления напоминаниями (включение, интервал, время начала и конца) и доступа к разделам «О приложении» и «Важная информация».
Rationale: Пользователь должен иметь возможность подстроить приложение под себя.
Acceptance Criteria: Изменённые значения сохраняются и применяются сразу; при вводе значения вне допустимого диапазона показывается сообщение об ошибке.
Verification Method: Test.

REQ-INT-007: Нижняя навигация

Title: Переходы между главными экранами.
Statement: Система должна предоставлять нижнюю навигацию с пунктами «Дневник», «Вода», «Прогресс», «Настройки», доступную на всех главных экранах.
Rationale: Быстрый доступ к главным разделам в одно нажатие.
Acceptance Criteria: Переход на любой из четырёх экранов выполняется за одно нажатие; текущий пункт подсвечен.
Verification Method: Demonstration.

REQ-INT-008: Пустые состояния и сообщения об ошибках

Title: Понятные сообщения.
Statement: Экраны со списками и графиками должны показывать понятное сообщение и подсказку действия в пустом состоянии и при ошибках.
Rationale: Пользователь не должен видеть пустой экран и гадать, что делать.
Acceptance Criteria: Для пустого дня показано «Нет записей за этот день. Нажмите «+», чтобы добавить еду»; для отсутствия сети и отказа в доступе к камере выводится сообщение с предложением действия (например, «Ввести вручную»).
Verification Method: Test.

REQ-INT-009: Язык интерфейса

Title: Русский язык.
Statement: Все тексты экранов, уведомлений и сообщений об ошибках должны быть на русском языке.
Rationale: Требование заказчика и целевой аудитории.
Acceptance Criteria: При обходе всех экранов и уведомлений нет текстов на других языках (кроме названий брендов и названий единиц измерения).
Verification Method: Inspection.

Юзабилити и доступность: интерфейс должен строиться по рекомендациям Material Design, использовать понятные состояния ошибок (например, «Продукт не найден», «Нет подключения к интернету») и учитывать системный размер шрифта Android. Визуальные макеты описаны в отдельных артефактах (модели SysMLv2 и PNG-макеты в разделе 5).

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

REQ-INT-010: Использование камеры

Title: Сканирование штрих-кодов камерой.
Statement: Система должна использовать основную камеру смартфона для сканирования штрих-кодов форматов EAN-13, EAN-8 и UPC-A.
Rationale: Это основной способ быстро найти продукт без ручного ввода.
Acceptance Criteria: Распознаётся штрих-код каждого из трёх форматов на реальных упаковках.
Verification Method: Test.

REQ-INT-011: Разрешение на камеру

Title: Запрос разрешения только при необходимости.
Statement: Система должна запрашивать разрешение на камеру только при первом открытии сканера и должна оставаться полностью работоспособной без этого разрешения (кроме сканирования).
Rationale: Минимальный набор разрешений повышает доверие пользователя.
Acceptance Criteria: При отказе в разрешении все функции, кроме сканера, доступны; на экране сканера показано сообщение и кнопка «Ввести вручную».
Verification Method: Test.
More Information: Негативный сценарий: пользователь запретил камеру навсегда – система объясняет, как включить доступ в настройках устройства.

REQ-INT-012: Размеры экранов и масштаб шрифта

Title: Адаптация под устройства.
Statement: Система должна корректно отображаться на экранах смартфонов с диагональю от 4,7" до 6,9" и сохранять читаемость при увеличении системного шрифта до 130%.
Rationale: Пользователи используют разные устройства и настройки доступности.
Acceptance Criteria: Вёрстка не ломается на эмуляторах с малым и большим экраном; при шрифте 130% текст не обрезается и кнопки остаются доступными.
Verification Method: Test.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

REQ-INT-013: Интеграция с API Open Food Facts

Title: Получение данных о продукте по штрих-коду.
Statement: Система должна получать данные продукта запросом к API Open Food Facts (HTTPS, формат JSON): название, калории, белки, жиры, углеводы на 100 г.
Rationale: Позволяет не вводить данные вручную и не поддерживать собственную базу продуктов.
Acceptance Criteria: Для известного штрих-кода получены название и калорийность на 100 г.
Verification Method: Test.
More Information: Подробности проверки данных – в REQ-AI-003 и REQ-AI-004.

REQ-INT-014: Обработка ошибок внешнего сервиса

Title: Поведение при сбоях API.
Statement: При таймауте (10 секунд), отсутствии сети или кодах ответа 4xx и 5xx система должна сообщить об ошибке и предложить ручной ввод, не завершаясь аварийно.
Rationale: Внешний сервис может быть недоступен, но работа приложения продолжаться должна.
Acceptance Criteria: В режиме полёта и при недоступном сервисе выводится сообщение, приложение остаётся работоспособным.
Verification Method: Test.

REQ-INT-015: Система уведомлений Android

Title: Показ напоминаний.
Statement: Система должна использовать систему уведомлений Android для напоминаний о воде и запрашивать разрешение на уведомления на Android 13 и выше.
Rationale: Без разрешения напоминания не будут показаны.
Acceptance Criteria: Уведомление приходит по расписанию при выданном разрешении; без разрешения в настройках показывается предупреждение.
Verification Method: Test.

REQ-INT-016: Локальное хранилище

Title: База данных на устройстве.
Statement: Система должна хранить продукты, записи питания и воды и настройки в локальной базе данных (Room, SQLite).
Rationale: Данные должны быть доступны без интернета и не передаваться вне устройства.
Acceptance Criteria: Структура базы соответствует словарю данных (раздел 5.4); данные доступны после перезапуска приложения.
Verification Method: Inspection.

### 3.2 Функциональные требования {#32-functional}

Учёт питания

REQ-FUNC-001: Ручное добавление записи о приёме пищи

Statement: Система должна позволять пользователю добавить запись: название, масса порции (г), калории, белки, жиры, углеводы, тип приёма пищи, дата и время.
Rationale: Базовая функция учёта; работает без камеры и интернета.
Acceptance Criteria: Запись сохраняется и отображается в дневнике выбранной даты; поля «название» и «калории» обязательны.
Verification Method: Test
More Information: Негативный сценарий: масса вне диапазона 1–5000 г, калории вне диапазона 0–5000 ккал на запись или пустое название – система показывает ошибку и запись не сохраняет.

REQ-FUNC-002: Добавление продукта сканированием штрих-кода

Statement: Система должна по сканированию штрих-кода находить продукт в Open Food Facts, подставлять название и пищевую ценность на 100 г и пересчитывать калории и БЖУ на введённую пользователем массу порции.
Rationale: Сокращает время ввода и количество ошибок при ручном вводе.
Acceptance Criteria: От наведения камеры до экрана с найденным продуктом проходит не более 5 секунд при хорошей связи и освещении; при порции 150 г и калорийности 200 ккал на 100 г отображается 300 ккал.
Verification Method: Test
More Information: См. REQ-INT-010, REQ-INT-013, REQ-AI-007. Граничный случай: пользователь может изменить любое поле перед сохранением.

REQ-FUNC-003: Продукт не найден или данные неполные

Statement: Если продукт не найден или у него нет данных о калориях, система должна сообщить об этом и предложить заполнить карточку вручную; введённый продукт должен сохраняться локально и находиться при повторном сканировании того же штрих-кода без обращения к сети.
Rationale: Open Food Facts не покрывает все продукты.
Acceptance Criteria: Для несуществующего штрих-кода показано сообщение и форма ручного ввода с уже заполненным штрих-кодом; при повторном сканировании продукт находится в режиме «без сети».
Verification Method: Test
More Information: Сценарий деградации: при недоступности сервиса поведение определяется REQ-INT-014.

REQ-FUNC-004: Дневник питания за выбранную дату

Statement: Система должна показывать записи за выбранную дату, сгруппированные по приёмам пищи, с суммарными калориями и БЖУ за каждую группу и за день, и позволять редактировать и удалять записи.
Rationale: Основной экран приложения.
Acceptance Criteria: Итоги за день равны сумме записей; после редактирования и удаления итоги обновляются сразу; можно выбрать любую дату в прошлом.
Verification Method: Test
More Information: Удаление записи требует подтверждения или предоставляет возможность отмены.

REQ-FUNC-005: Недавние и избранные продукты

Statement: Система должна показывать при добавлении записи список недавних продуктов (последние 20) и позволять отметить продукт избранным.
Rationale: Пользователи часто едят одно и то же, поэтому повторный ввод должен быть быстрым.
Acceptance Criteria: Продукт из списка добавляется в дневник не более чем за 3 нажатия; избранные отображаются выше недавних; продукт можно убрать из избранного.
Verification Method: Demonstration
Цели и вода

REQ-FUNC-006: Дневная цель по калориям

Statement: Система должна позволять пользователю задать дневную цель по калориям и показывать остаток или превышение на экране дневника.
Rationale: Без цели невозможно оценить прогресс.
Acceptance Criteria: Допустимые значения цели 800–6000 ккал; цель по умолчанию 2000 ккал; при превышении цели индикатор меняет цвет и отображается превышение в ккал.
Verification Method: Test
More Information: Изменение цели не меняет данные прошлых дней. Нижняя граница ограничивает риск неверного использования приложения (см. REQ-COMP-002 и REQ-AI-005).

REQ-FUNC-007: Учёт выпитой воды

Statement: Система должна позволять добавлять порции воды кнопками быстрого ввода (150, 250, 500 мл), вводом произвольного объёма и отменять последнее добавление.
Rationale: Вода записывается много раз за день, ввод должен занимать одно нажатие.
Acceptance Criteria: Нажатие кнопки быстрого ввода добавляет запись и обновляет итог за день менее чем за 1 секунду; произвольный объём принимается в диапазоне 10–2000 мл; отмена последней записи уменьшает итог.
Verification Method: Test
More Information: Негативный сценарий: объём вне диапазона или пустое поле – система показывает ошибку и запись не добавляет. Список записей воды за день можно просмотреть и удалить запись.

REQ-FUNC-008: Дневная цель по воде

Statement: Система должна позволять задать дневную цель по воде и показывать прогресс в процентах и миллилитрах.
Rationale: Цель мотивирует и определяет логику напоминаний.
Acceptance Criteria: Цель по умолчанию 2000 мл, допустимый диапазон 500–6000 мл; при достижении цели показывается сообщение о выполнении.
Verification Method: Test
More Information: Прогресс может превышать 100%.
Напоминания и прогресс

REQ-FUNC-009: Напоминания о воде

Statement: Система должна присылать уведомления о необходимости выпить воду с интервалом от 30 минут до 4 часов в заданном пользователем окне времени (по умолчанию 09:00–21:00), позволять включать и отключать напоминания и не присылать уведомления после достижения дневной цели.
Rationale: Напоминания – одна из ключевых бизнес-целей продукта.
Acceptance Criteria: Уведомление приходит в пределах ±2 минут от расчётного времени при выданном разрешении; вне окна времени уведомлений нет; после достижения цели уведомления до следующего дня не приходят; из уведомления можно добавить порцию воды без открытия приложения.
Verification Method: Test
More Information: См. REQ-INT-015, REQ-REL-004. Если уведомления отключены в системе, в настройках показывается предупреждение (сценарий деградации).

REQ-FUNC-010: Прогресс за день

Statement: Система должна показывать прогресс за день (индикатор калорий и воды) на экранах «Дневник» и «Вода».
Rationale: Мгновенная обратная связь после каждого ввода.
Acceptance Criteria: Индикаторы обновляются сразу после добавления, редактирования или удаления записи; значения совпадают с суммами записей.
Verification Method: Test

REQ-FUNC-011: Графики за 7 и 30 дней

Statement: Система должна показывать графики калорий и воды за последние 7 и 30 дней с отметкой цели и средними значениями за период.
Rationale: Наглядная динамика повышает вовлечённость.
Acceptance Criteria: Данные на графиках совпадают с суммами по дням в дневнике; переключение 7/30 дней занимает менее 1 секунды.
Verification Method: Test
More Information: Дни без записей отображаются явно как отсутствие данных, а не как ноль.
Вспомогательные функции

REQ-FUNC-012: Первый запуск и информационное сообщение

Statement: Система должна при первом запуске показывать краткое описание возможностей и сообщение о том, что приложение не является медицинским средством, и сохранять факт подтверждения.
Rationale: Пользователь должен понимать назначение приложения и его границы.
Acceptance Criteria: Сообщение показывается один раз при первом запуске и остаётся доступным в разделе «Важная информация».
Verification Method: Demonstration
More Information: См. REQ-COMP-002.

REQ-FUNC-013: Экспорт данных

Statement: Система может позволять экспортировать записи за выбранный период в CSV-файл.
Rationale: Позволяет пользователю сохранить данные и передать их специалисту.
Acceptance Criteria: Файл открывается в табличном редакторе и содержит дату, название, массу, калории, БЖУ и объём воды.
Verification Method: Test

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

Все целевые показатели производительности измеряются на смартфоне среднего класса (4 ГБ оперативной памяти, Android 10 и выше) при базе данных объёмом до одного года записей.

Подкатегория: Время (задержка и скорость отклика)

REQ-PERF-001: Время запуска

Statement: Холодный запуск приложения до отображения экрана «Дневник» не должен превышать 3 секунд.
Rationale: Долгий запуск мешает быстро внести запись и снижает удобство.
Acceptance Criteria: Среднее время из 10 холодных запусков не более 3 секунд.
Verification Method: Test
More Information: Относится к REQ-INT-001.

REQ-PERF-002: Открытие экранов и построение графиков

Statement: Открытие дневника со 100 записями и построение графика за 30 дней не должны превышать 1 секунды.
Rationale: Просмотр данных должен быть мгновенным (REQ-FUNC-004, REQ-FUNC-011).
Acceptance Criteria: Замер на тестовой базе со 100 записями в день и 365 днями данных показывает время не более 1 секунды.
Verification Method: Test
More Information: Должно быть учтено при проектировании индексов базы данных.

REQ-PERF-003: Распознавание штрих-кода

Statement: Распознавание штрих-кода камерой должно занимать не более 3 секунд при нормальном освещении.
Rationale: Сканирование – главное конкурентное преимущество продукта.
Acceptance Criteria: Не менее 90% из 20 реальных штрих-кодов распознаются не дольше чем за 3 секунды.
Verification Method: Test
More Information: См. REQ-AI-001.

REQ-PERF-004: Отклик на нажатие

Statement: Реакция интерфейса на нажатие кнопки (визуальный отклик) не должна превышать 100 мс, а добавление порции воды кнопкой быстрого ввода должно отображаться в итогах не позднее чем через 1 секунду.
Rationale: Быстрый отклик создаёт ощущение надёжности приложения.
Acceptance Criteria: При ручных замерах 20 нажатий среднее время визуального отклика не более 100 мс.
Verification Method: Test

Подкатегория: Пространство (ресурсы)

REQ-PERF-005: Объём данных на устройстве

Statement: Приложение вместе с данными за один год использования должно занимать не более 100 МБ на устройстве.
Rationale: Приложение не должно занимать много места в памяти телефона.
Acceptance Criteria: Размер приложения и данных после генерации тестовых данных за 365 дней не превышает 100 МБ.
Verification Method: Analysis

#### 3.3.2 Безопасность {#332-security}

Все компоненты системы должны проектироваться с учётом базовых принципов безопасности. Требования разделены на логические подкатегории.

Подкатегория: Хранение и приватность данных

REQ-SEC-001: Локальное хранение и минимальная передача данных

Statement: Пользовательские данные (записи питания, воды, цели) должны храниться только на устройстве. Единственная информация, которая отправляется во внешние сервисы, – штрих-код продукта.
Rationale: Защищает приватность пользователя и упрощает соответствие законодательству.
Acceptance Criteria: При анализе сетевого трафика единственные исходящие запросы – к API Open Food Facts, и они содержат только штрих-код.
Verification Method: Analysis
More Information: См. REQ-AI-002, REQ-COMP-004.

REQ-SEC-002: Минимальный набор разрешений

Statement: Приложение должно запрашивать только разрешения на камеру, доступ в интернет и показ уведомлений.
Rationale: Лишние разрешения снижают доверие и расширяют поверхность атаки.
Acceptance Criteria: В манифесте приложения нет других разрешений.
Verification Method: Inspection

REQ-SEC-003: Шифрование при передаче данных (HTTPS)

Statement: Весь обмен с внешним сервисом должен идти только по защищённому протоколу HTTPS.
Rationale: Защищает данные от перехвата и подмены.
Acceptance Criteria: Запрос по протоколу HTTP не выполняется приложением.
Verification Method: Test

REQ-SEC-006: Исключение из облачных резервных копий

Statement: Данные приложения следует исключить из автоматических облачных резервных копий Android либо предупреждать пользователя об этом при первом запуске.
Rationale: Данные о питании могут считаться чувствительными, и пользователь должен контролировать, где они хранятся.
Acceptance Criteria: В параметрах резервного копирования приложения данные исключены либо при первом запуске показано соответствующее сообщение.
Verification Method: Inspection

Подкатегория: Защита от некорректных данных

REQ-SEC-004: Валидация вводимых данных

Statement: Все данные, вводимые пользователем (названия продуктов, массы, объёмы, цели), должны проверяться на допустимые диапазоны и длину до сохранения.
Rationale: Защищает от ошибочных данных и нарушения целостности хранилища.
Acceptance Criteria: Названия длиной более 100 символов, пустые значения и значения вне диапазонов, заданных в REQ-FUNC-001, 006, 007, 008, не сохраняются, пользователю показывается ошибка.
Verification Method: Test

REQ-SEC-005: Защита от SQL-инъекций

Statement: При работе с базой данных система должна использовать параметризованные запросы (через Room) и не собирать SQL из пользовательского текста.
Rationale: Предотвращает искажение и потерю данных через специально составленный ввод.
Acceptance Criteria: Ввод в поле названия строки вида ' OR 1=1 -- сохраняется как обычный текст и не влияет на запросы.
Verification Method: Test

#### 3.3.3 Надёжность {#333-reliability}

REQ-REL-001: Сохранность данных

Statement: Система должна сохранять все введённые записи при закрытии приложения, аварийном завершении процесса и перезагрузке телефона.
Rationale: Потеря данных за день сильно снижает доверие к приложению.
Acceptance Criteria: После принудительного завершения процесса и перезагрузки ранее сохранённые записи на месте.
Verification Method: Test
More Information: Запись добавляется в базу атомарно: либо сохранена полностью, либо нет.

REQ-REL-002: Работа без интернета

Statement: Все функции, кроме получения данных нового продукта по штрих-коду, должны работать без интернета.
Rationale: Пользователь может находиться вне зоны покрытия.
Acceptance Criteria: В режиме полёта работают дневник, вода, графики, напоминания и сохранённые продукты.
Verification Method: Test

REQ-REL-003: Стабильность

Statement: Доля сеансов без аварийного завершения должна быть не ниже 99%.
Rationale: Стабильность напрямую влияет на готовность пользователя вести ежедневный учёт.
Acceptance Criteria: На тестовом прогоне из 100 сценариев приходится не более одного краха.
Verification Method: Test

REQ-REL-004: Сохранность расписания напоминаний

Statement: Расписание напоминаний о воде должно сохраняться и восстанавливаться после перезагрузки телефона и обновления приложения.
Rationale: После перезагрузки пользователь не должен заново включать напоминания.
Acceptance Criteria: После перезагрузки устройства уведомления приходят по прежнему расписанию без запуска приложения.
Verification Method: Test

#### 3.3.4 Доступность {#334-availability}

REQ-AVAIL-001: Автономная работа

Statement: Локальная часть приложения должна быть доступна круглосуточно и не должна зависеть от внешних сервисов.
Rationale: У приложения нет серверной части, поэтому его доступность определяется только устройством пользователя.
Acceptance Criteria: При недоступности всех внешних сервисов работают все функции, кроме сканирования новых продуктов.
Verification Method: Test

REQ-AVAIL-002: Деградация при недоступности Open Food Facts

Statement: При недоступности Open Food Facts система должна продолжать работу, предлагая ручной ввод и показывая ранее сохранённые продукты.
Rationale: Сбой внешнего сервиса не должен останавливать учёт.
Acceptance Criteria: При отключённой сети сканер находит ранее сохранённые продукты, а для новых предлагается ручной ввод.
Verification Method: Test

#### 3.3.5 Наблюдаемость {#335-observability}

REQ-OBS-001: Технический журнал ошибок

Statement: Приложение должно вести локальный технический журнал ошибок (без персональных данных и записей питания) и позволять отправить его разработчику по желанию пользователя.
Rationale: Журнал помогает находить причины сбоев без передачи личных данных.
Acceptance Criteria: Журнал содержит время и тип ошибки, но не содержит названий продуктов; отправка выполняется только по действию пользователя.
Verification Method: Inspection

### 3.4 Соответствие стандартам {#34-compliance}

Система «NutriFlow» должна соответствовать требованиям законодательства Республики Беларусь, а также правилам использования сторонних сервисов, интегрированных в приложение.

REQ-COMP-001: Лицензия данных Open Food Facts

Statement: Система должна соблюдать условия лицензии ODbL при использовании данных Open Food Facts и указывать источник данных на экране «О приложении».
Rationale: Нарушение условий лицензии может привести к запрету на использование данных.
Acceptance Criteria: В разделе «О приложении» указан источник данных и размещена ссылка на лицензию.
Verification Method: Inspection

REQ-COMP-002: Информирование о границах приложения

Statement: Система должна показывать при первом запуске и в настройках уведомление о том, что приложение не является медицинским средством и не заменяет консультацию специалиста.
Rationale: Приложение ведёт учёт, но не даёт медицинских рекомендаций, и пользователь должен это понимать.
Acceptance Criteria: Уведомление отображается при первом запуске, принимается пользователем и доступно в разделе «Важная информация».
Verification Method: Inspection

REQ-COMP-003: Лицензии сторонних библиотек

Statement: Используемые сторонние библиотеки (CameraX, ZXing, Room, MPAndroidChart и др.) должны иметь лицензии, допускающие их использование в проекте, и быть перечислены в репозитории.
Rationale: Использование библиотек вне условий лицензии нарушает права авторов.
Acceptance Criteria: В репозитории есть список библиотек с их версиями и лицензиями.
Verification Method: Inspection

REQ-COMP-004: Защита персональных данных

Statement: Система должна обрабатывать данные пользователя в соответствии с Законом РБ «О защите персональных данных» (№ 99-З от 07.05.2021): данные хранятся на устройстве, не передаются третьим лицам, а сведения об этом доступны в разделе «О приложении».
Rationale: Данные о питании и привычках относятся к личной информации пользователя.
Acceptance Criteria: В разделе «О приложении» описано, какие данные хранятся и что они не передаются; анализ трафика подтверждает отсутствие передачи личных данных (REQ-SEC-001).
Verification Method: Inspection

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

Приложение должно устанавливаться на смартфон без дополнительного программного обеспечения и настройки окружения пользователем.

REQ-INST-001: Установка из APK-файла

Statement: Приложение должно устанавливаться из APK-файла на Android 8.0 и выше без дополнительного ПО.
Rationale: Простая установка нужна для демонстрации проекта преподавателю и заказчику.
Acceptance Criteria: Установка и первый запуск на чистом устройстве проходят без действий, кроме выдачи разрешений.
Verification Method: Demonstration

REQ-INST-002: Секреты вне репозитория

Statement: Ключи подписи приложения и пароли к ним не должны храниться в исходном коде и публичном репозитории.
Rationale: Предотвращает утечку секретов при публикации кода на GitHub.
Acceptance Criteria: В репозитории отсутствуют файлы хранилища ключей и пароли; в .gitignore указаны соответствующие файлы.
Verification Method: Inspection

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

Процесс сборки должен быть стандартизирован, чтобы любой разработчик мог собрать проект локально и запустить его.

REQ-BUILD-001: Сборка проекта одной командой

Statement: Сборка приложения должна выполняться системой сборки Gradle одной командой, результатом должен быть APK-файл.
Rationale: Стандартный способ сборки Android-приложения без ручных шагов.
Acceptance Criteria: Команда ./gradlew assembleDebug успешно завершается (BUILD SUCCESSFUL), а APK-файл появляется в каталоге сборки.
Verification Method: Test

REQ-BUILD-002: Фиксация версий зависимостей

Statement: Версии используемых библиотек должны быть строго зафиксированы в конфигурационных файлах Gradle.
Rationale: Предотвращает ситуацию, когда проект перестаёт собираться из-за выхода новой версии сторонней библиотеки.
Acceptance Criteria: В файлах сборки у всех зависимостей указаны конкретные версии без диапазонов и «latest».
Verification Method: Inspection

REQ-BUILD-003: Подписанная релизная сборка

Statement: Релизная сборка должна подписываться ключом разработчика.
Rationale: Подписанный APK можно устанавливать на устройства и обновлять.
Acceptance Criteria: Команда сборки релиза создаёт подписанный APK, который устанавливается на устройство.
Verification Method: Test

#### 3.5.3 Распределение {#353-distribution}

В текущей версии продукта (MVP) система является автономным приложением на устройстве пользователя.

REQ-DIST-001: Автономное приложение

Statement: Все компоненты системы (интерфейс, логика, база данных) должны находиться внутри одного мобильного приложения; серверные компоненты проекта отсутствуют.
Rationale: Упрощает архитектуру, снижает затраты на инфраструктуру и защищает приватность данных.
Acceptance Criteria: В проекте нет серверных модулей; все данные пользователя хранятся на устройстве.
Verification Method: Inspection

#### 3.5.4 Сопровождаемость {#354-maintainability}
Система должна проектироваться с учётом того, что код будет дорабатываться и изменяться в будущем (как автором, так и другими разработчиками).

REQ-MAINT-001: Слоистая архитектура

Statement: Код должен быть разделён на слои: интерфейс, бизнес-логика, доступ к данным.
Rationale: Изменения в одном слое не должны ломать остальные.
Acceptance Criteria: Классы экранов не содержат запросов к базе данных и расчётов калорий; расчёты вынесены в отдельные классы.
Verification Method: Inspection

REQ-MAINT-002: Стиль кода

Statement: Код следует оформлять в соответствии с Google Java Style Guide.
Rationale: Единый стиль упрощает чтение и поддержку кода.
Acceptance Criteria: Проверка стиля (например, Checkstyle) не выдаёт критических замечаний.
Verification Method: Inspection

REQ-MAINT-003: Модульные тесты бизнес-логики

Statement: Бизнес-логика (подсчёт калорий и БЖУ, воды, итогов за день, проверка данных) должна быть покрыта модульными тестами.
Rationale: Тесты позволяют безопасно менять код.
Acceptance Criteria: Покрытие тестами бизнес-логики не ниже 70%.
Verification Method: Analysis

REQ-MAINT-004: Работа через Git

Statement: Разработка должна вестись в системе контроля версий Git: отдельные ветки для задач, осмысленные коммиты, слияние через Pull Request.
Rationale: История изменений прозрачна, а ошибки можно отменить.
Acceptance Criteria: В репозитории есть ветки и Pull Requests с описанием изменений.
Verification Method: Inspection

#### 3.5.5 Повторное использование {#355-reusability}

REQ-REUSE-001: Заменяемый источник данных о продуктах

Statement: Модуль доступа к данным о продуктах следует выделить за отдельным интерфейсом так, чтобы источник данных можно было заменить без изменения экранов.
Rationale: Источник данных (Open Food Facts) может измениться или стать недоступным.
Acceptance Criteria: Источник данных заменяется другой реализацией интерфейса без правок классов экранов.
Verification Method: Inspection

#### 3.5.6 Переносимость {#356-portability}

REQ-PORT-001: Платформы и устройства

Statement: Приложение должно работать на смартфонах с Android 8.0 (API 26) и выше с разными размерами экрана. Версии для iOS и web не входят в область проекта.
Rationale: Разработка ведётся на Java, нативно поддерживаемой Android SDK.
Acceptance Criteria: Проверка пройдена на эмуляторах с двумя размерами экрана и нескольких версиях Android.
Verification Method: Test

#### 3.5.7 Стоимость {#357-cost}

REQ-COST-001: Отсутствие платных сервисов

Statement: Разработка и эксплуатация должны обходиться без платных сервисов, лицензий и подписок.
Rationale: Учебный проект не имеет бюджета.
Acceptance Criteria: В проекте используются только бесплатные библиотеки и бесплатный API.
Verification Method: Inspection используются платные API
Verification Method: Inspection

#### 3.5.8 Сроки {#358-deadline}

REQ-DEAD-001: Выполнение по итерациям

Statement: Итерации 1–3 (см. 2.6) должны быть выполнены в сроки, установленные графиком курса ЖЦРПО; конкретные даты уточняются у преподавателя.
Rationale: Результаты должны быть готовы к плановым контрольным точкам курса.
Acceptance Criteria: Версия каждой итерации принята преподавателем в назначенную дату.
Verification Method: Demonstration

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}

REQ-POC-001: Прототип сканирования

Statement: До начала итерации 2 должен быть проверен прототип: сканирование штрих-кода и получение данных из Open Food Facts для 10 популярных товаров.
Rationale: Сканирование – самый рискованный технический элемент проекта, его нужно проверить раньше остальных.
Acceptance Criteria: Данные получены не менее чем для 8 из 10 товаров, время ответа не более 5 секунд.
Verification Method: Demonstration

#### 3.5.10 Управление изменениями {#3510-change-management}

REQ-CM-001: Порядок внесения изменений

Statement: Изменения требований должны вноситься через Pull Request в отдельную ветку с обновлением истории изменений документа; правки преподавателя в ходе занятия вносятся до его окончания.
Rationale: Прозрачный процесс снижает затраты на переделку.
Acceptance Criteria: Каждое изменение отражено в истории изменений и в Pull Request.
Verification Method: Inspection
