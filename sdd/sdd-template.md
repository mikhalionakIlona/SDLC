## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Данный документ описывает архитектуру и основные проектные решения мобильного приложения NutriFlow. Он предназначен для разработчика, заказчика и лиц, проверяющих соответствие реализации требованиям. Документ используется как руководство при разработке, тестировании и дальнейшем сопровождении приложения; он дополняет материалы предыдущей лабораторной работы и ADR-001.

### 1.2 Область применения {#12-subject-scope}

NutriFlow — мобильное приложение для Android, предназначенное для ведения дневника питания и учета водного баланса. Пользователь может добавлять приемы пищи вручную, находить продукты по штрихкоду, учитывать выпитую воду, устанавливать дневные цели, получать напоминания и просматривать статистику за 7 и 30 дней. Приложение ориентировано на локальное хранение пользовательских данных и работу основных функций без подключения к интернету.

В проект входят: дневник питания, расчет калорий и БЖУ, учет воды, дневные цели, локальная база данных, сканирование штрихкодов, получение сведений о продуктах из Open Food Facts, напоминания и статистика. В текущую версию не входят backend, регистрация, синхронизация между устройствами, iOS, веб-версия, распознавание еды по фотографии и медицинские рекомендации.

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}

Для описания NutriFlow используются точки зрения, перечисленные в шаблоне. Они раскрывают границы системы, состав модулей, структуру данных, взаимодействия и особенности выполнения на Android. Для некоторых пунктов описание ограничено особенностями проекта: отдельная серверная инфраструктура и распределенная система отсутствуют.

#### 2.2.1 Контекст {#221-context}

NutriFlow рассматривается как система, взаимодействующая со следующими внешними сущностями:
- Пользователь — добавляет продукты и воду, задает цели, просматривает статистику.
- Камера Android-устройства — используется для считывания штрихкода.
- Open Food Facts — внешний каталог, из которого по штрихкоду запрашиваются сведения о продукте.
- Android OS — предоставляет разрешения, уведомления, планирование фоновых задач и файловые механизмы.
Основные сервисы системы: ведение дневника питания, учет воды, расчет дневных показателей, сканирование штрихкодов, напоминания и просмотр статистики. Внешний каталог используется только для получения информации о продукте; собственный сервер приложения не предусмотрен.

#### 2.2.2 Композиция {#222-composition}

Система состоит из следующих функциональных частей:
1. Presentation/UI — экраны дневника, добавления продукта, сканера, воды, целей и статистики.
2. Food Module — создание и изменение продуктов и записей о приемах пищи.
3. Barcode Module — получение изображения с камеры и распознавание штрихкода с помощью CameraX и ZXing.
4. Water Module — добавление и просмотр записей о воде.
5. Goals Module — хранение и применение дневных целей.
6. Reminder Module — настройка и планирование напоминаний через WorkManager и уведомления Android.
7. Statistics Module — агрегирование записей и подготовка данных для графиков MPAndroidChart.
8. Data Module — репозитории, DAO и локальная база Room/SQLite.
9. External API Adapter — запросы к Open Food Facts и преобразование полученного ответа в модель продукта.
UI не обращается напрямую к SQL-запросам или внешнему API: доступ выполняется через репозитории.

#### 2.2.3 Логическое представление {#223-logical}

Основные логические сущности системы:

| Сущность | Основные поля | Назначение |
|---|---|---|
| FoodProduct | id, name, barcode, caloriesPer100g, proteinPer100g, fatPer100g, carbsPer100g, source | Описание продукта и его пищевой ценности |
| MealEntry | id, dateTime, mealType, productId, amountGrams, calories, protein, fat, carbs | Запись о продукте в конкретном приеме пищи |
| WaterEntry | id, dateTime, amountMl | Запись об объеме выпитой воды |
| DailyGoal | id, caloriesTarget, waterTargetMl | Дневные цели пользователя |
| ReminderSettings | id, enabled, startTime, endTime, intervalMinutes | Настройки напоминаний |
| FavoriteProduct | productId | Связь пользователя с избранным продуктом |

MealEntry связан с FoodProduct через productId. Значения калорий и БЖУ записи определяются количеством продукта. Данные группируются по календарной дате для отображения дневных итогов.

#### 2.2.4 Физическое представление {#224-physical}

Система предназначена для работы на физическом Android-устройстве или эмуляторе под управлением Android 8.0 и выше. Для сканирования штрихкодов требуется камера устройства. Для получения данных о неизвестном продукте требуется доступ к интернету. Пользовательские данные хранятся в приватной области приложения на устройстве.

Отдельные серверы, серверные стойки, облачные узлы и сетевая топология в проекте отсутствуют, поэтому более подробная физическая схема не требуется.

#### 2.2.5 Структура {#225-structure}

Логическая структура приложения разделена на пакеты:
- ui — Activity, Fragment, адаптеры и элементы экранов;
- domain — модели и правила расчетов;
- data — репозитории;
- database — Room Database, DAO и Entity;
- barcode — работа камеры и декодирование штрихкодов;
- notifications — настройки и запуск напоминаний;
- statistics — подготовка агрегированных данных и графиков;
- integration — взаимодействие с Open Food Facts.
Связь между частями организуется через методы репозиториев и модели данных. UI-компоненты не должны содержать SQL-запросы и бизнес-правила расчета.

#### 2.2.6 Зависимости {#226-dependency}

Основные зависимости компонентов:
- UI использует Domain и интерфейсы репозиториев.
- Food Module использует FoodRepository и MealRepository.
- Water Module использует WaterRepository.
- Goals Module использует GoalRepository.
- Barcode Module использует CameraX, ZXing и FoodRepository.
- External API Adapter выполняет HTTP-запрос к Open Food Facts и возвращает данные FoodRepository.
- Reminder Module использует WorkManager и Android Notifications.
- Statistics Module получает данные через репозитории и формирует наборы значений для MPAndroidChart.
- Репозитории используют DAO Room для чтения и записи локальных данных.
Таким образом, интерфейс зависит от логики приложения, а не от конкретного способа хранения данных.

#### 2.2.7 Информация {#227-information}

Постоянные данные хранятся в локальной базе Room/SQLite. Для продукта пищевая ценность задается на 100 граммов. Для конкретной записи значения рассчитываются пропорционально указанной массе. Вода хранится в миллилитрах, масса продукта — в граммах, дата и время записи используются для группировки по дням.

При удалении или изменении MealEntry дневные итоги и статистика должны учитывать актуальные записи. Если продукт отсутствует во внешнем каталоге или интернет недоступен, пользователь может создать продукт вручную. Данные дневника не требуют сетевого соединения для просмотра и редактирования.

#### 2.2.8 Интерфейс {#228-interface}

Пользовательский интерфейс включает следующие экраны:
- Дневник — список приемов пищи за выбранную дату и дневные итоги.
- Добавление продукта — ручной поиск/ввод продукта, массы и типа приема пищи.
- Сканер — получение штрихкода камерой и отображение найденного продукта.
- Вода — добавление объема воды и просмотр суммы за день.
- Цели и напоминания — настройка дневных целей и расписания напоминаний.
- Статистика — графики показателей за 7 и 30 дней.
Интерфейс реализуется на XML с использованием Material Components. При отсутствии разрешения на камеру или уведомления приложение должно сообщить пользователю о необходимости разрешения. При недоступности Open Food Facts показывается сообщение, а ручное добавление продукта остается доступным.

#### 2.2.9 Взаимодействие {#229-interaction}

Сценарий сканирования штрихкода:
1. Пользователь открывает сканер.
2. Приложение проверяет разрешение камеры и при необходимости запрашивает его.
3. CameraX передает изображение, ZXing распознает штрихкод.
4. Приложение проверяет наличие штрихкода в локальной базе.
5. Если продукт не найден локально и доступна сеть, выполняется запрос к Open Food Facts.
6. Полученные сведения показываются пользователю для подтверждения.
7. После подтверждения продукт и запись о приеме пищи сохраняются через репозиторий и Room.
Сценарий отказа: если камера недоступна, разрешение отклонено, сеть отсутствует или продукт не найден, приложение показывает соответствующее сообщение и предлагает ручной ввод. Сбой внешнего сервиса не должен приводить к потере уже сохраненных записей.

#### 2.2.10 Алгоритм {#2210-algorithm}

Расчет пищевой ценности для записи выполняется по формуле:

Значение записи = Значение на 100 г × Масса порции / 100.

Дневные калории, белки, жиры и углеводы вычисляются как сумма соответствующих значений всех MealEntry за выбранную дату. Количество воды за день вычисляется как сумма WaterEntry.amountMl за ту же дату.

Прогресс цели рассчитывается как Фактическое значение / Целевое значение × 100%, если целевое значение больше нуля. Отображаемый процент может быть ограничен 100%, при этом фактическое значение сохраняется без ограничения.

#### 2.2.11 Динамика состояний {#2211-state-dynamics}

Для сканера предусмотрены состояния:
Idle → RequestingPermission → Scanning → ProductFound / ProductNotFound / Error → Confirming → Saved.

Переходы:
- Idle → RequestingPermission — пользователь запускает сканер.
- RequestingPermission → Scanning — разрешение предоставлено.
- RequestingPermission → Error — разрешение не предоставлено.
- Scanning → ProductFound — штрихкод распознан и продукт найден.
- Scanning → ProductNotFound — код распознан, но продукт не найден.
- ProductFound → Confirming — сведения показаны пользователю.
- Confirming → Saved — пользователь подтверждает добавление.
Для напоминаний предусмотрены состояния Disabled и Scheduled. При отключении напоминаний запланированная задача отменяется; при изменении расписания старая задача заменяется новой.

#### 2.2.12 Параллелизм {#2212-concurrency}

Приложение не является распределенной или многопользовательской системой. Тем не менее отдельные операции выполняются асинхронно: сетевые запросы к Open Food Facts и операции с базой данных не должны блокировать UI-поток. Фоновые напоминания запускаются через WorkManager. Обновление интерфейса выполняется после получения результата операции.

Для предотвращения повторных напоминаний при повторном планировании необходимо отменять или заменять предыдущую задачу с тем же идентификатором/уникальным именем.

#### 2.2.13 Паттерны {#2213-patterns}

В проекте используются следующие архитектурные и проектные подходы:
- Repository — отделяет UI и бизнес-логику от источника данных.
- DAO — инкапсулирует операции чтения и записи Room.
- Разделение слоев — UI, логика приложения, данные и интеграции находятся отдельно.
- Observer / lifecycle-aware наблюдение — позволяет обновлять экран при изменении данных с учетом жизненного цикла Android-компонентов.
Другие паттерны, не требуемые текущим объемом проекта, отдельно не вводятся.

#### 2.2.14 Развёртывание {#2214-deployment}

Результат сборки — APK для устройств с Android 8.0 и выше. Сборка выполняется средствами Android Studio и Gradle. Для проверки приложение устанавливается на эмулятор или физическое устройство. Локальная база создается на устройстве при первом запуске; отдельное серверное развертывание не требуется.

#### 2.2.15 Ресурсы {#2215-resources}

Для разработки и работы приложения используются:
- рабочая станция с Android Studio;
- JDK 17 и Android SDK;
- Android-эмулятор или физическое устройство с Android 8.0+;
- камера устройства для проверки сканирования;
- доступ к интернету для проверки Open Food Facts;
- локальное хранилище устройства для базы данных;
- разрешение Android на отправку уведомлений для проверки напоминаний.

## 3. Проектные представления {#3-design-views}

3.1 [001]-Контекст приложения
- ID: 001-Context
- Title: Контекст приложения NutriFlow
- Viewpoint: Контекст
- Representation: Пользователь взаимодействует с Android-приложением. Приложение использует камеру устройства, локальную БД Room/SQLite, системные уведомления и внешний каталог Open Food Facts. Основные функции дневника выполняются локально; внешний сервис нужен только для получения информации о продукте по штрихкоду.
- More Information: Разделы 1.2 и 2.2.1. Связанные требования: FR-01—FR-09, NFR-02, NFR-06.
3.2 [002]-Компоненты приложения
- ID: 002-Composition
- Title: Функциональные компоненты NutriFlow
- Viewpoint: Композиция
- Representation: UI, Food Module, Barcode Module, Water Module, Goals Module, Reminder Module, Statistics Module, Data Module и External API Adapter. Компоненты доступа к данным отделены от пользовательского интерфейса.
- More Information: Разделы 2.2.2 и 2.2.6. Связанные требования: FR-01—FR-09, NFR-08.
3.3 [003]-Модель данных
- ID: 003-DataModel
- Title: Логическая модель данных
- Viewpoint: Логическое представление / Информация
- Representation: Сущности FoodProduct, MealEntry, WaterEntry, DailyGoal, ReminderSettings и FavoriteProduct хранятся локально. MealEntry ссылается на FoodProduct; дневные показатели рассчитываются по записям за выбранную дату.
- More Information: Разделы 2.2.3 и 2.2.7. Связанные требования: FR-01, FR-02, FR-03, FR-04, FR-05, FR-07.
3.4 [004]-Сценарий сканирования
- ID: 004-BarcodeFlow
- Title: Последовательность сканирования штрихкода
- Viewpoint: Взаимодействие
- Representation: Пользователь запускает сканер; приложение проверяет разрешение камеры; CameraX получает изображение; ZXing декодирует код; выполняется локальный поиск, а при необходимости — запрос Open Food Facts; после подтверждения продукт сохраняется в Room. При ошибке сети или отсутствии продукта доступен ручной ввод.
- More Information: Разделы 2.2.8 и 2.2.9. Связанные требования: FR-06, FR-07, NFR-07.
3.5 [005]-Расчет дневных показателей
- ID: 005-DailyCalculation
- Title: Расчет калорий, БЖУ и воды
- Viewpoint: Алгоритм
- Representation: Пищевая ценность порции рассчитывается пропорционально массе: значение на 100 г умножается на массу и делится на 100. Дневные значения калорий и БЖУ суммируются по MealEntry, вода — по WaterEntry за выбранную дату.
- More Information: Раздел 2.2.10. Связанные требования: FR-02, FR-03, FR-04.
3.6 [006]-Фоновая работа и напоминания
- ID: 006-BackgroundTasks
- Title: Планирование напоминаний
- Viewpoint: Параллелизм / Динамика состояний
- Representation: WorkManager планирует фоновые задачи по параметрам пользователя. При отключении напоминаний задача отменяется; при изменении расписания предыдущая задача заменяется. Уведомления отображаются средствами Android.
- More Information: Разделы 2.2.11 и 2.2.12. Связанные требования: FR-08, NFR-07.
3.7 [007]-Развёртывание Android
- ID: 007-Deployment
- Title: Развёртывание на Android-устройстве
- Viewpoint: Развёртывание
- Representation: APK устанавливается на Android 8.0+. Room хранит данные в приватной области приложения. Камера, уведомления и фоновые задачи предоставляются Android OS.
- More Information: Разделы 2.2.4 и 2.2.14. Связанные требования: NFR-01, NFR-02, NFR-06.

## 4. Решения {#4-decisions}

4.1 [ADR-001]-Нативная Android-архитектура
- ID: ADR-001
- Title: Выбор нативной Android-архитектуры с локальным хранением данных
- Context: NutriFlow должен обеспечивать дневник питания и воды, дневные цели, сканирование штрихкодов, напоминания и статистику. Основные функции должны работать офлайн. Backend, регистрация и синхронизация не входят в границы проекта.
- Options:
  1. Нативное Android-приложение на Java с Room/SQLite, CameraX/ZXing и WorkManager.
  2. Кроссплатформенное приложение, например Flutter.
  3. Веб-приложение с серверной базой данных.
- Outcome: Выбран вариант 1 — нативное Android-приложение. Он соответствует платформе и границам проекта, обеспечивает локальное хранение и прямой доступ к возможностям Android. Вариант Flutter добавляет стек и интеграционные зависимости для платформ, которые сейчас не требуются. Веб-вариант предполагает сервер и постоянную сетевую инфраструктуру, не предусмотренные проектом.
- More Information: Подробное обоснование приведено в отдельном документе NutriFlow_ADR-001.md. Связанные представления: 001-Context, 002-Composition, 003-DataModel, 007-Deployment.
4.2 [ADR-002]-Добавление экспорта CSV
- ID: ADR-002
- Title: Локальное формирование CSV-файла без серверной отправки
- Context: По результатам учебной переговорной симуляции заказчик добавил возможность экспорта дневника питания в CSV, при этом дата выпуска не должна сдвигаться. Требование должно соответствовать локально-ориентированной архитектуре NutriFlow.
- Options:
  1. Формировать CSV на устройстве из локальной базы и сохранять файл средствами Android.
  2. Отправлять данные на сервер и формировать файл на серверной стороне.
  3. Не включать экспорт в текущую версию.
- Outcome: Выбран вариант 1. Он не требует backend, регистрации или передачи пользовательских данных внешнему серверу. Первая версия ограничивается CSV и выбором периода; сложное форматирование Excel и облачная отправка не выполняются.
- More Information: Требование FR-10. Реализация запланирована на третью итерацию с привлечением junior-разработчика под контролем основного разработчика. Дополнительная оценка и переговоры приведены в отчете по лабораторной работе №4.
